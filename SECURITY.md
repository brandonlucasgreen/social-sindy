# Security policy

## Reporting a vulnerability

Please do **not** open a public issue for a security problem.

Report it privately through GitHub's
[private vulnerability reporting](https://github.com/brandonlucasgreen/social-sindy/security/advisories/new),
or by email to **hi@bgreen.lol**.

This is a personal project maintained by one person. Expect an acknowledgement
within a week. There is no bounty program.

## Scope

This repository is the whole product: one Cloudflare Worker serving
`socialsindy.com`, plus two legacy hostnames routed to the same Worker.

Especially interested in reports about:

- **Feed token handling.** `/feed/:token.ics` and `/feed/:token.xml` authenticate
  on an unguessable token alone and sit deliberately outside the session and CSRF
  middleware. Anything that lets one user's token be guessed, enumerated, or
  leaked into a log or a cache key is in scope.
- **Cross-tenant data access.** Any path where one account's posts, channels, or
  stored credentials become reachable from another account's session or token.
- **Stored credential exposure.** Buffer access and refresh tokens are sealed
  with AES-256-GCM (`src/crypto.ts`). Anything that surfaces plaintext — in a
  response body, an error message, or a log line — is in scope.
- **OAuth flow flaws.** PKCE verifier handling, `state` validation, or redirect
  URI handling in `src/buffer/oauth.ts` and `src/google/oauth.ts`.
- **Session and CSRF.** Session cookie handling in `src/session.ts`, or a
  mutating route reachable without the CSRF middleware.

Out of scope:

- Missing hardening headers with no demonstrated impact.
- Rate limiting on public pages. Feed responses are cached in KV specifically so
  that polling cannot drain a user's Buffer quota; a report that polling is
  possible is not itself a finding.
- Reports generated by a scanner with no verified exploit path.
- The `POST /connect` legacy route accepting a pasted Buffer API key. This is
  known and documented in the README: the path is removed from the UI, retained
  only so accounts created that way keep working, and signing in with OAuth
  deletes any key still stored.

## What this app can reach

Scopes are deliberately narrow, so the blast radius of a compromise is bounded:

- **Buffer:** `account:read`, `posts:read`, `offline_access`. No post can be
  created, edited, or deleted. This is structural, not a policy promise.
- **Google:** `calendar.app.created` only — access is limited to calendars this
  app itself created; it cannot read or modify any pre-existing calendar. This
  integration is currently disabled in the deployed app.

## Secrets

No credentials belong in this repository. `ENCRYPTION_KEY`,
`BUFFER_CLIENT_SECRET`, and `GOOGLE_CLIENT_SECRET` are set with
`wrangler secret put` and exist only in Cloudflare.

The OAuth **client IDs** in `wrangler.toml` are public by design — a client ID
ships in the redirect URL every user's browser follows. The D1 database ID and KV
namespace ID there are resource identifiers, not credentials; they are useless
without authenticated access to the Cloudflare account.

CI holds no secrets. If you believe a real credential has been committed, report
it privately rather than opening an issue.
